3. 瓶颈分析

3.1 DNS 瓶颈

默认 ISP DNS 服务器通常解析延迟高 (50-200ms)，且无恶意域名过滤。现代网页平均包含 30-80 个外部资源请求，每次请求触发 DNS 查询。

⚠️ 量化影响: 页面有 50 个外部资源 + 100ms DNS 延迟 = 5 秒总 DNS 等待。
切换到 10ms DNS 后 = 0.5 秒，节省 4.5 秒。

3.2 TCP 拥塞控制瓶颈

CUBIC (Linux 默认) 是基于丢包的算法。在跨洋或高延迟链路中，少量丢包就会导致吞吐量断崖式下降。

场景 (300ms RTT, 0.1% 丢包)平均吞吐量
CUBIC~15 Mbps
BBR~80 Mbps
提升: 5.3 倍
💡 原因: CUBIC 将丢包等同于拥塞（在现代网络中经常误判），BBR 则持续测量带宽和 RTT 来建模真实链路容量。

3.3 队列管理瓶颈 (Bufferbloat)

默认 pfifo_fast 队列会造成 bufferbloat——当发送缓冲区被填满时，延迟暴增数百毫秒。
BBR 需要 fq (Fair Queue) 进行精确的流量 pacing。在出口接口上额外配置 fq_codel 防止 bufferbloat。

3.4 TCP 缓冲区瓶颈

BDP (带宽-延迟积) 计算:

BDP = 带宽(bps) × RTT(s) / 8

1 Gbps × 300ms = 37.5 MB
100 Mbps × 50ms = 625 KB

如果 TCP 缓冲区 < BDP，吞吐量 = 缓冲区/RTT (受限于缓冲区而非带宽)

4.5 MTU 路径优化 & PPPoE 适配

⚠️ PPPoE 链路警告: 标准以太网 MTU = 1500，但 PPPoE 拨号链路（光猫拨号）的实际链路 MTU = 1492。
这 8 字节的差异会导致满尺寸 TCP 包被强制分片，在移动国际出口这种有损链路上放大丢包效应。

自动检测：脚本通过 ip link show 检测 ppp 接口，通过 traceroute 检测双层 NAT 拓扑（光猫+路由器）。

MSS 钳制 (核心修复)：

# 计算: MSS = 路径 MTU - 40 (IP头 + TCP头)
# PPPoE 场景: MTU 1492 → MSS 1452

# 对本机发出的 TCP SYN 包重写 MSS
sudo iptables -t mangle -A OUTPUT -p tcp --tcp-flags SYN,RST SYN \
    -j TCPMSS --set-mss 1452

# 对转发的流量同样处理
sudo iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
    -j TCPMSS --set-mss 1452

PMTU 发现作为辅助：

# 启用内核 MTU 探测（作为 ICMP 路径的备份）
sudo sysctl -w net.ipv4.tcp_mtu_probing=1

# 放行 ICMP 分片需要消息（PMTU 发现工作所需，但运营商可能丢弃）
sudo iptables -A INPUT -p icmp --icmp-type fragmentation-needed -j ACCEPT
sudo iptables -A INPUT -p icmp --icmp-type destination-unreachable -j ACCEPT

# 手动探测 PMTU
ping -M do -s 1472 223.5.5.5
# 逐步减小 size 直到 ping 成功，PMTU = 成功size + 28
✅ 关键认知: MSS 钳制 不依赖 ICMP Fragmentation Needed 消息。
它直接在 SYN 握手阶段重写 MSS 字段——即使中间运营商丢弃所有 ICMP，分片问题仍被彻底解决。

7. 技术原理

7.1 BBR 拥塞控制

BBR (Bottleneck Bandwidth and Round-trip propagation time) 是 Google 发布的拥塞控制算法，于 Linux 4.9 合入主线。

传统算法 vs BBR:

特性CUBIC/RenoBBR
检测方式基于丢包基于带宽-延迟测量
丢包响应大幅缩减窗口不直接响应丢包
bufferbloat会填满缓冲区避免填满
有损链路性能急剧下降保持高吞吐
RTT 公平性RTT 短的流占优RTT 公平
💡 BBR 工作流程:
1. 持续测量瓶颈带宽 (BtlBw) 和往返传播时间 (RTprop)
2. 计算 BDP = BtlBw × RTprop
3. 控制发送速率 = BDP
4. 周期性探测更高带宽 (PROBE_BW 阶段)

7.2 TCP Fast Open

标准 TCP 三次握手: Client Server |------ SYN -------------------→| |←----- SYN+ACK ---------------| |------ ACK + DATA ------------→| ← 数据在第 3 步才开始 RTT 浪费: 1 TCP Fast Open: Client Server |------ SYN + TFO Cookie + DATA →| ← 数据在第 1 步就开始! |←----- SYN+ACK + DATA ---------| RTT 节省: 1

7.3 fq_codel 队列管理

fq_codel (Fair Queuing Controlled Delay) 同时解决两个问题：

  1. 公平队列: 隔离不同流的流量，防止一个大流量流饿死小流量流
  2. 受控延迟: 监控每个包的排队延迟，超时则丢包（向发送端发出拥塞信号）

7.4 MTU 与 PMTU 发现

MTU: 网络接口能发送的最大单个数据包。标准以太网 MTU = 1500 字节。

PMTU: 从源到目标路径上所有链路的最小 MTU。

源头 ──── MTU 1500 ──── 路由器 ──── MTU 1492 ──── 目标 ↑ 瓶颈 MTU = 1492

PMTU 发现过程: 发送端发出带 DF 标志的包 → 中间路由器若 MTU 太小则返回 ICMP "Fragmentation Needed" → 发送端降低包大小重试 → 收敛到路径最小 MTU。

9. 故障排除

❌ BBR 无法启用
sysctl: cannot stat .../bbr: No such file or directory
解决: 1) 内核版本需 >= 4.9；2) sudo modprobe tcp_bbr；3) 如模块不存在，升级内核。
⚠️ DNS 更改后无法上网
解决: 1) ping 1.1.1.1 确认可达；2) 检查 resolv.conf；3) 临时回退: echo 'nameserver 8.8.8.8' | sudo tee /etc/resolv.conf
⚠️ MTU 问题导致部分网站无法访问
症状: 小文件正常，大文件超时。
原因: 路径 MTU 小于默认值，ICMP 被防火墙阻止。
解决: 手动探测 PMTU 或启用 MSS 钳制。
⚠️ 大量 TIME_WAIT 连接
检查: sysctl net.ipv4.tcp_tw_reuse 应为 1；net.ipv4.tcp_fin_timeout 应为 15
